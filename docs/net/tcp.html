Reliable stream or best-effort datagrams? TCP and UDP over the same lossy path

An app sends the same photo over TCP and over UDP. Both lanes cross an identical network: the same delay, the same bottleneck and the same packets lost on their first try. Watch TCP segment, acknowledge and retransmit, while UDP delivers whatever happens to arrive. Click any packet in flight to drop it.

      What to notice

      • Segmentation versus message boundaries. TCP cuts the socket's byte stream into MSS-sized segments on its own; the app's write() boundaries are lost. UDP sends exactly what each sendto() hands it, so the app decides the chunking, and an oversized datagram is split by IP instead.
      • Loss detection. TCP learns about loss from duplicate ACKs (fast retransmit, about one RTT) or from its retransmission timer (RTO, much slower and followed by cwnd = 1). UDP never finds out; the gap stays in the picture.
      • Head-of-line blocking. Segments that arrive after a gap wait in TCP's receive buffer (yellow) until the missing one is retransmitted, so the app sees nothing new even though the data is already there. UDP hands every datagram up immediately, in whatever order it arrives.
      • Cost of reliability. TCP spends a round trip on the handshake, sends ACKs, slows down after loss and resends data; UDP finishes sooner with less overhead, but incompletely.
      • Which to choose. File transfer, web pages, SCADA configuration or firmware pushes need every byte: TCP (or QUIC). Voice, video and fast periodic telemetry often prefer fresh data over late data: UDP with application-level handling. One lost IP fragment destroys an entire large UDP datagram.

      Model simplifications: TCP follows Reno/NewReno without SACK, ACKs every segment, and uses a shortened RTO (RFC 6298 recommends a 1 s minimum). Handshake packets are never lost. The IP reassembly timeout is shortened for the demo (real stacks wait around 30 s). Bottleneck: one 1,500-byte packet every 16 ms (≈ 0.75 Mb/s).
